## Что сейчас находится на SprintHost

PHP-релиз bc700ee загружен в public_html 25 ноября 2026 г. из архива tokyo-premium-release-bc700ee-2026-11-25.zip. Архив содержал приложение и локальные ресурсы, но не SQLite, .env или .htaccess. Существующий .htaccess сохранён.

- PHP-приложение использует SQLite в `private-data/`, вне `public_html`; хостовая конфигурация сохраняет `SetEnv RESTAURANT_DB`. Повторная проверка: `/.env` и `/schema.sql` — HTTP 403, `/seed.sql` — HTTP 200 (11 351 байт). Репозиторный `.htaccess` запрещает SQL-файлы, но правило ещё не объединено с серверным файлом; после ручного входа добавить запрет, сохранив `SetEnv RESTAURANT_DB` и остальные строки.
- Перед обновлением создан закрытый архив активной базы: private-data/tokyo-restaurant-public50.pre-v22-2026-11-25.tar.gz. Активную базу не заменяли копией из Git и не переносили в web-каталог.
- В активной базе до выкладки было 52 блюда (50 публичных и 2 Secret Menu), 8 категорий, 36 аккаунтов, 104 заказа, 305 строк заказа, 52 брони, 34 отзыва, 76 записей лояльности, 6 сезонных коллекций и 39 связей коллекций с блюдами. Это снимок до миграции; контактные поля и строки пользователей не публикуются.
- После выкладки страница привилегий показывает коллекцию Hanami in Kyoto, добавленную миграцией 22. Это подтверждает, что приложение применило необходимое расширение данных при запуске; блюд в каталоге по-прежнему 50.
- Проверены ответы HTTP 200 и отсутствие PHP fatal/warning/exception/SQLSTATE у главной, меню, Omakase, привилегий, философии, пространства, отзывов, контактов, бронирования, корзины, кабинета и сборщика сета. В браузере отдельно открыты меню, бронирование, кабинет, Omakase и админка; меню показывает 50 блюд.
- Админка доступна, но первого администратора нет: страница предлагает создать его командой php setup_admin.php. Скрипт работает только через CLI и должен использовать тот же RESTAURANT_DB. Входы или пароли не создавались и не проверялись на незащищённом HTTP.
- Прямой GET /payment.php без подписанного действия возвращает ожидаемый 404; никаких заказов, броней или платежей при проверке не отправляли.
- Технический домен f1338748.xsph.ru работает по HTTP. Не вводить через него реальные пароли, персональные или платёжные данные. Для HTTPS нужен уже принадлежащий владельцу домен с сертификатом либо другой уже доступный PHP-хостинг с HTTPS. Покупок или смены тарифа не было; баланс панели — 0 ₽.
- Приложению нужен SQLite, не MySQL/PostgreSQL; отдельный DbaaS не создан. База и секреты не входят в Git.
- Публичная статическая версия GitHub Pages остаётся отдельной демонстрацией: она не исполняет PHP и не пишет в серверную SQLite.
## Оставшиеся задачи по приоритету

### P0 — довести PHP-развёртывание до безопасного администрирования

- [ ] После повторного входа в SprintHost открыть текущий `public_html/.htaccess` и добавить запрет на раздачу всех `*.sql` (по правилу из репозитория), сохранив `SetEnv RESTAURANT_DB` и остальные серверные строки. Не заменять серверный файл целиком. Затем подтвердить, что `/seed.sql` и `/schema.sql` отвечают 403 или 404, а главная и меню остаются 200.

- [ ] После устранения утечки безопасно выложить актуальный PHP-исходник из main в `public_html`, не трогая серверный `.htaccess`, `.env` и SQLite; проверить, что PHP Omakase показывает 5 подач и основные маршруты/каталог работают.
- [ ] Подключить валидный HTTPS на домене владельца или перенести PHP-приложение на уже доступный HTTPS-хостинг. Технический домен .xsph.ru остаётся HTTP-only; покупку домена/тарифа без отдельного решения владельца не выполнять.
- [ ] После появления HTTPS создать первого администратора через php setup_admin.php, запущенный в CLI с RESTAURANT_DB, указывающим на ту же активную SQLite вне public_html. Сгенерировать уникальный пароль и передать его владельцу безопасным способом; не помещать его в Git или URL.
- [ ] На HTTPS-хосте выполнить безопасный smoke-test с отдельной тестовой записью: вход/выход админа, сессия, права и просмотр каталога/заявок. Не использовать реальные контакты и не отправлять тестовую оплату/бронь посетителям.
- [ ] Для дальнейших обновлений сохранять текущий порядок: резервная копия активной БД → выкладка кода без .htaccess и данных → проверка миграции и маршрутов → проверка восстановления резервной копии.
